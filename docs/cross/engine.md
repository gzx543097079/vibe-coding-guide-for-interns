跨端运行时把业务代码变成屏幕、事件和系统调用。理解它的目标是**定位开销发生在哪一层**，而不是凭一张架构图判断某框架永远更快。

## 几类路径

| 路线 | 可以观察的边界 | 典型开销来源 |
| --- | --- | --- |
| Web / WebView | DOM、样式、脚本与宿主插件 | 主线程工作、布局和容器通信 |
| 自有渲染体系 | 组件树、布局、绘制与引擎 | 重建范围、图形资源和平台集成 |
| 原生组件体系 | JS / 共享层与原生 UI | 状态传播、数据转换和原生工作 |
| 共享业务逻辑 | 公共模块与平台实现 | 数据边界、调度与平台差异 |

这是分析视角，不是排他的产品分类。框架会演进，同一产品也可能组合多条路径；对照工程实际版本查架构，尤其不要把旧桥接资料当作当前所有实现。

## 从输入到一帧画面

用户事件进入运行时，业务逻辑更新状态，框架决定更新哪些界面，平台或引擎安排布局、绘制和合成。异步请求和原生回调还会在稍后重新触发这个过程。

如果某次操作卡顿，先看是脚本计算、布局、图片、平台调用还是 GPU 相关工作。降低某层开销后，瓶颈可能转移；单看 JavaScript 执行时间不能解释完整的用户等待。

## 数据传递也有成本

高频传输大对象、逐项跨层调用、重复编码和解码都可能放大开销。适当批量处理与减少冗余更新有帮助，但批量过大也会影响响应。用相同设备和数据测量，而不是把调用次数减少直接等同于体验提升。

让 Codex 根据性能记录解释一条具体调用链，标出线程、数据复制和等待位置；先修改一个主要因素，再对比真实目标端。浏览器假界面或调试模式的表现不能替代发布构建的设备测量。
