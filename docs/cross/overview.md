大前端把 Web、原生客户端、小程序和桌面应用放在同一套交付视角下考虑；跨端框架尝试复用其中一部分代码。**复用的是哪些层、差异留在哪里，比「一套代码」的宣传更重要。**

## 先按目标平台筛选

| 路线 | 常见复用范围 | 主要代价 |
| --- | --- | --- |
| 原生开发 | 领域模型、协议和部分业务逻辑 | 各端界面与工程分别维护 |
| Flutter | Dart 业务与大部分 UI 描述 | 引擎、平台插件与端差异治理 |
| React Native | React / TypeScript 与原生组件组织 | 原生工程、依赖与架构版本适配 |
| uni-app / Taro | 受框架约束的页面与业务代码 | 各目标端支持差异与编译限制 |
| Web 容器类方案 | Web 页面和部分系统能力封装 | 容器、安全、离线和原生体验 |

不要只比较首个页面的实现速度。相机、支付、推送、后台任务、无障碍与发布流程，往往决定长期维护成本。

## 用一个纵向切片做验证

挑一个真实但可控的流程，例如登录后读取列表并打开详情。让它穿过路由、请求、状态、原生能力和打包流程；分别在主要目标端运行。只做静态首页，很难发现桥接、签名和生命周期问题。

## 给团队的选型记录

```text
目标端和最低支持范围是什么？
已有成员熟悉哪些语言与原生工程？
必须调用哪些系统能力，插件是否满足实际要求？
怎样测试平台差异，谁维护发布和框架升级？
如果方案不满足要求，哪些业务代码可以保留？
```

这些问题用于团队做决策，不是要求每章复述的固定模板。记录实际实验结果，不给没有测过的方案标记「性能最好」。

让 Codex 实现跨端功能时，明确框架、目标端和原生插件边界。编译成功只覆盖一个目标和配置；一个端能跑，不代表其他端已经完成验证。
