跨端发布需要把**源码、框架工具链、原生依赖、签名与环境配置**组织成可重复流程。共享代码只有一份，不代表每个目标端使用相同的构建和审核方式。

## 为每个目标保存发布记录

| 记录项 | 用途 |
| --- | --- |
| commit 与依赖锁定 | 确认源码和工具输入 |
| 目标与构建变体 | 区分开发、体验、测试和正式产物 |
| 签名与凭据来源 | 确认由授权环境注入，不进源码 |
| 配置与后端兼容范围 | 避免测试地址进入正式包 |
| 产物标识与验证结果 | 能追溯实际安装和测试的包 |

同一版本名称下重新构建，仍可能产生不同产物。保留构建标识和摘要，比只记一个展示版本号更可靠。

## 发布前走一次真实安装路径

开发服务器里的热重载不能验证正式包。使用对应产物安装、登录、读取数据和调用关键系统能力；检查升级后旧数据、离线与权限状态是否仍可用。

```text
请整理现有工程各目标端的构建脚本与配置来源。
先报告签名、环境变量和版本信息如何注入，不读取凭据值。
列出测试包与正式包的差异，以及尚未跑过的验证。
只准备构建和发布说明，不自动上传或提交审核。
```

## 热更新有技术与平台边界

哪些内容能够更新、是否允许改变原生能力、如何处理版本兼容和失败恢复，要同时符合框架机制及目标平台当前要求。不要把某个框架支持热更新，理解为任何代码都能绕过商店审核。

实际提交、签名权限和正式发布由有权限的负责人按流程执行。回退也可能受客户端安装版本与数据迁移限制；需要提前准备兼容后端和可关闭的功能入口，而不是只保存旧安装包。
