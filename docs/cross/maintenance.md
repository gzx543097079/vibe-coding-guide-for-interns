---
title: 跨端项目的长期维护
description: 框架升级、依赖治理与平台差异的长期成本。
---

跨端项目的长期成本来自**框架、插件、原生 SDK 和平台规则同时变化**。维护策略应让问题尽早暴露，并能识别是哪一层变化导致回归。

## 保存一份真实支持矩阵

记录目标平台、最低系统 / 基础库、工具链、框架、关键插件和最后验证的产物。矩阵应来自工程配置和实际运行记录，不把包管理器上的最新版本自动视为团队支持版本。

| 变更 | 需要检查的影响 |
| --- | --- |
| 框架升级 | 编译配置、组件行为、状态与导航 |
| 插件升级 | 原生依赖、权限、返回结构和失败语义 |
| 系统 SDK 升级 | 废弃 API、签名、构建和平台限制 |
| 后端协议变化 | 旧客户端兼容与缓存数据 |

## 升级分阶段做

先让当前版本的构建和关键测试可重复，再在独立分支升级一类依赖，按官方迁移说明处理差异。保留升级前后的产物和关键流程记录；不要同时重构业务、替换状态库和升级所有原生插件。

## 把端差异集中在边界

共享逻辑保持业务含义稳定，平台能力通过适配层暴露。差异说明要写清原因、适用范围和移除条件，避免条件编译不断累积成另一套难读代码。

```text
评估当前工程升级一个主要框架版本的影响。
先列依赖约束、迁移项与插件兼容性，不修改锁文件。
按风险给出最小验证路径和可撤回步骤。
无法核实的支持情况标明来源与未决项。
```

每次发布都验证主要目标端的关键路径，低频使用的目标也要有明确维护负责人。若某端长期无人能构建或安装，应如实调整支持范围，而不是只因为编译选项仍存在就继续承诺支持。
