一旦跨进程或跨网络调用，就必须面对**对方是否执行、响应是否丢失、双方状态是否一致**。超时只说明调用方没有按时得到结果，不证明服务端没有完成操作。

## 超时、重试和幂等一起设计

| 情况 | 不能直接做的事 | 更合理的处理 |
| --- | --- | --- |
| 创建订单超时 | 无条件再次创建 | 用业务请求标识查询或幂等重试 |
| 下游持续失败 | 所有请求立刻高频重试 | 限制次数、退避并观察恢复 |
| 多个服务同时过载 | 每层都独立多次重试 | 协调总预算，防止重试放大 |
| 返回不完整数据 | 把降级结果当成正常完整结果 | 明确降级语义和恢复方式 |

网络调用要有合理的连接、读取或总时间预算，具体能力取决于客户端实现。日志保留关联 ID 和重试原因，但不打印敏感载荷。

## 一致性先从业务不变量讲起

订单、库存和支付位于不同系统时，本地事务无法自动覆盖全部动作。可以考虑消息驱动、outbox、补偿或其他协调方案；每种方式都要说明失败后谁继续推进，以及用户会看到什么中间状态。

补偿不是时间倒流。例如已经发送的邮件无法真正撤回，退款也不是删除原支付记录。把过程保存成可追溯的状态变化，通常比捕获异常后「全部清空」更可靠。

## 按真实故障验证

在隔离环境中模拟响应延迟、重复消息、消费者重启和部分依赖不可用。检查最终业务不变量，例如没有重复扣款、事件不会永久丢失、处理中状态能继续恢复。

让 Codex 给出方案时，要求画清数据所有者、状态变化、重试与恢复责任，不只列几个中间件名称。规模不需要时，优先在单库事务和清晰模块内完成需求，避免提前引入无法维护的分布式流程。
