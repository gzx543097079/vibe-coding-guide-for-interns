后端架构首先让**业务规则、数据访问和外部协议各有清楚位置**。项目规模不大时，模块清楚的单体通常更容易测试和维护；微服务需要额外处理网络、部署与数据一致性。

## 依赖方向比目录名字更重要

```text
HTTP / 消息入口 → 应用用例 → 领域规则
                         → 数据访问与外部服务接口
```

入口层解析和验证协议数据，用例组织一次业务动作，领域规则表达业务不变量，适配层连接数据库和外部服务。具体项目不必强行复制这些目录，但不要把所有业务都写进路由处理函数。

| 边界 | 需要明确的约定 |
| --- | --- |
| 配置 | 来源、默认值、缺失时是否启动失败 |
| 日志 | 请求关联、事件、耗时与敏感字段过滤 |
| 错误 | 哪些可重试、哪些返回给调用方 |
| 数据 | 事务归谁管理，谁可以直接写表 |
| 外部依赖 | 超时、熔断、重试与降级 |

## 服务拆分需要真实理由

独立扩缩容、团队交付边界和故障隔离可以成为拆分依据；仅因为文件多，不足以证明需要网络调用。拆出去之后，原本的函数调用会变成可能超时、失败和重复的远程操作。

先把单体内的模块接口稳定下来，再评估部署拆分。共享数据库表会把服务重新绑在一起，不能只看进程数量判断是否解耦。

## 让配置与运行状态可解释

配置可以从环境注入，但不要把所有环境变量或完整配置打印进日志。启动时验证必要配置，健康检查区分进程还活着与业务依赖是否可用。测试环境应能复现关键流程，不依赖开发者本机隐藏的服务。

给 Codex 重构任务时，指定要改善的调用链、应保持的接口和可运行测试。先调整一个边界，确认行为保持，再继续；不要边重构边升级数据库或改变业务语义。
