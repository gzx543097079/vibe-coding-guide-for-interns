---
title: 高可用与容量规划
description: 冗余、降级、限流与容量评估。
---

高可用不是「部署两个实例」，容量规划也不是先买更大的机器。先定义**关键业务的可接受失败、响应时间与恢复目标**，再检查系统中哪些环节会成为单点或瓶颈。

## 从依赖链和用户影响开始

| 机制 | 解决的问题 | 需要验证的边界 |
| --- | --- | --- |
| 冗余与故障切换 | 单实例或单节点失败 | 切换时间、共享依赖与数据状态 |
| 限流 | 超过可承受的请求量 | 公平性、错误反馈与重试行为 |
| 降级 | 非关键依赖失效 | 业务是否接受不完整功能 |
| 超时与隔离 | 某个依赖拖住整体 | 线程、连接与队列资源 |
| 备份与恢复 | 数据丢失或损坏 | 恢复耗时和数据缺口 |

多个实例共享同一个不可恢复的数据库，仍存在关键单点。自动扩容也有启动和预热延迟，不能消除所有突发流量。

## 用负载模型代替猜测

记录请求类型、数据量、读写比例、并发模式、缓存状态和依赖行为。逐步增加负载，观察延迟分布、错误率和资源饱和；找到容量拐点后留出适合业务的余量，不凭 CPU 没满判断系统还有无限空间。

容量结果必须带环境与条件。测试小数据库、热缓存和短请求得到的数字，不应直接用来承诺真实生产容量。

## 把恢复过程练习出来

在授权的隔离环境中检查实例退出、依赖不可用和恢复后的行为，明确谁观察、谁决策、谁执行。破坏性演练不能让 Agent 自行对线上系统发起。

```text
根据现有监控与压测记录，找出最先饱和的资源。
给出限流、降级或扩容方案，说明用户会看到的行为。
列出验证条件、风险和恢复步骤，不直接调整生产配置。
```

可用性与成本、复杂度相互制约。选择能被团队持续维护和验证的方案，而不是把所有高可用名词都装进系统。
