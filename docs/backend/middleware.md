缓存、消息队列、对象存储和搜索服务解决不同问题。引入之前先明确**主数据在哪里、失败时谁负责恢复、是否真的需要增加一个运行组件**。

## 常见服务与边界

| 服务 | 解决什么 | 必须设计的失败路径 |
| --- | --- | --- |
| 缓存 | 降低重复读取与部分计算成本 | 失效、过期、穿透和与主数据不一致 |
| 消息队列 | 解耦异步任务、缓冲工作 | 重复、积压、失败重试和死信 |
| 对象存储 | 保存文件与大对象 | 上传失败、访问控制和清理 |
| 搜索服务 | 检索、排序与聚合 | 索引延迟、重建与主数据同步 |

把数据放进 Redis，并不自动得到可靠的分布式锁或唯一执行。使用任何服务都要核对持久化、复制、超时与权限配置。

## 消息处理按可能重复设计

例如「订单创建后发送通知」：业务提交成功后可靠地产生事件，消费者按业务标识处理，成功后确认；失败时保留错误和重试次数。是否采用事务消息、outbox 或其他方案，要根据数据库与队列能力决定。

```json
{
  "event_id": "demo-event-1",
  "type": "order.created",
  "order_id": "demo-order-1"
}
```

这是业务事件示意，不包含真实用户数据。消费者不能因为收到两次事件就发送两次不可撤销的动作；幂等记录与业务更新需要有一致性设计。

## 缓存不是另一份随意维护的真相

说明键格式、租户范围、过期和主动失效方式。删除或更新主记录后，缓存如何改变，要能通过测试复现。不能把「缓存命中率高」当作缓存数据正确的证明。

让 Codex 接入中间件时，先给已有客户端封装与基础设施约定，再要求覆盖不可用、超时、重复和恢复场景。日志中不要打印连接凭据或完整消息中的敏感字段。
