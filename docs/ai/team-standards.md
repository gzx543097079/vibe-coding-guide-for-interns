团队规范要让不同成员和 Codex **按同一套可检查的边界交付**。把个人习惯直接写成几十条强制规则，往往只会产生冲突；先约定最常见、影响最大的行为。

## 一份可落地的项目约定

```md
# AGENTS.md
- 开始工作前读取 README 和相关模块说明。
- 只修改当前任务涉及的文件，公共接口变更需说明调用方影响。
- 完成后运行项目已有检查，报告命令与实际结果。
- 不读取凭据，不向未经授权的外部服务发送项目数据。
- 提交前检查 diff，在功能分支提 PR，由有权限的成员审核合并。
```

这份示例描述行为；真正的文件访问、网络和审批边界仍需单独配置。项目没有的 `lint` 或 `test` 命令不要照抄进去，应使用仓库实际存在的脚本。

## 规范也要有维护者

| 约定 | 谁应参与确认 | 什么情况下更新 |
| --- | --- | --- |
| 分支与合并流程 | 仓库维护者 | 发布节奏或协作方式变化 |
| 代码外发与数据范围 | 数据负责人及团队指定角色 | 服务、账号或数据用途变化 |
| 质量门槛 | 模块维护者 | 测试、构建和依赖变化 |
| 例外处理 | 任务负责人 | 当前任务无法满足既有约束 |

规则写明原因和替代办法，比简单地写「禁止」更容易执行。例如不能改公共接口时，说明可以新增兼容适配层，并要求补充契约测试。

## 用实际任务校对规则

拿一个正常任务、一个应被限制的任务和一个无关任务检查效果。无关规则不应干扰其他模块；重复出现的误解才值得补入长期约定。权限由程序执行，格式由工具检查，需要判断的兼容性和业务问题由审查者负责。

规则文件变更也走 PR，说明为何新增、影响哪些任务、旧约定是否已失效。不要让规则成为只有 Agent 知道、团队成员却从未读过的另一套流程。
