测试验证某段软件的行为，评测关注**一类 Agent 任务是否稳定达到要求**。一次对话成功只能证明那一次有结果，不能证明更换输入、模型或工具后仍然可靠。先定义什么叫失败，再谈通过率。

## 把验收拆成可检查的事实

修复 bug 可以检查原复现是否消失、回归测试是否通过、修改是否越界；生成接口可以检查字段契约、鉴权、错误响应和重复请求。不要只用「回答看起来专业」作为评分标准。

下面是权限规则练习的评测集结构，不是线上统计数据：

| 输入场景 | 期望行为 | 证据 |
| --- | --- | --- |
| 已允许的构建命令 | 命中对应规则 | 规则检查输出 |
| 需要审批的写入 | 进入规定审批流程 | 调用记录与决策 |
| 被禁止的动作 | 拒绝且不换方式绕过 | 拒绝记录和后续动作 |
| 工具返回失败 | 正确说明失败并处理 | 原始结果及后续调用 |

## 留下失败样例，不只留下漂亮输出

用稳定的输入、工具环境、模型配置和明确评分规则比较改动。保留正常、边界、权限不足、超时、外部内容带误导指令等场景；涉及真实业务数据时先脱敏并确认授权。

确定性的规则交给代码：文件是否越界、JSON 是否符合 schema、测试退出码等。业务正确性与说明质量可由人工评审；用模型打分时也要抽样校对，不能让可能犯同一种错误的模型既负责生成又负责裁判。

## 结果要能追到一次运行

记录输入、配置版本、工具调用、输出、评分依据和失败原因。先复现失败，再改提示词或实现，使用同一组样例比较前后；另外保留未参与调优的样例，避免只记住已见过的答案。

不必先接入托管评测平台。一个受版本管理的场景清单和可重复的运行脚本，已经能帮助发现回归；具体托管 API 的可用性以官方当前说明为准。
