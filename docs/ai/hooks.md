Hook 是**在特定事件发生时，由执行程序触发的检查或动作**。它适合反复运行且规则确定的工作，例如检查变更格式、验证构建、提示缺少交接记录。提示词让模型记住流程；Hook 则把一部分流程交给程序。

## 先分清触发位置

Codex 的生命周期 Hook 与 Git Hook、CI 不是一套机制：前者跟随会话和工具事件；Git Hook 跟随 Git 操作；CI 在提交或 PR 等事件后运行。检查应放在哪里，要看它必须何时发生、失败是否需要阻止后续动作。

| 场景 | 适合的位置 | 注意事项 |
| --- | --- | --- |
| 工具调用前校验参数 | 支持拦截的前置事件 | 不要把拒绝原因吞掉 |
| 修改后提示运行检查 | 后置事件 | 已发生的写入不会因此自动撤销 |
| 提交前检查暂存内容 | Git Hook | 本地可以被跳过，不能当作唯一门禁 |
| 合并前验证整站 | CI | 使用实际提交和一致的依赖环境 |

## 从一条可手动运行的脚本开始

本仓库已经有构建命令，可以先做一个独立脚本：

```sh
#!/usr/bin/env sh
set -eu
npm run build
```

保存为脚本后，在项目根目录手动运行，确认成功返回零、失败返回非零，再根据当前 Codex 文档配置触发事件。这里展示的是检查脚本，不是可直接复制为 Hook 配置的完整安装方案。

## 控制副作用和运行时间

Hook 不应悄悄格式化整个仓库、提交代码或上传日志。需要修改文件的自动化，要说明作用范围，并防止修改再次触发自身形成循环。耗时检查可放在提交或 CI 阶段，避免每读一次文件都跑整站构建。

Codex 的非托管 Hook 还涉及来源审查和信任设置；项目里的脚本会执行代码，应像依赖一样审查。事件名称、配置结构和信任入口会随版本演进，按 [官方 Hooks 文档](https://learn.chatgpt.com/docs/hooks) 接入，验证失败时不要用关闭信任检查来修复脚本。
