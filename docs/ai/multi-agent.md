---
title: 多 Agent 与子 Agent
description: 把检索、审查等子任务交给子 Agent，主 Agent 负责整合。
---

多 Agent 适合**可以独立产出、能清楚整合的子任务**。它不会自动提高正确率：多个模型可能共享同一种错误，也会增加上下文传递、等待、审查和费用。先判断单个 Agent 是否已经足够。

## 哪些工作适合分开

| 子任务 | 为什么可以独立 | 返回什么 |
| --- | --- | --- |
| 定位入口和调用方 | 可以只读，不修改实现 | 路径、调用关系和证据 |
| 核对一组 API 文档 | 数据来源相对独立 | 版本范围、官方链接和差异 |
| 审查已有 diff | 可以从验收条件重新检查 | 有复现条件的具体问题 |
| 实现不同模块 | 接口稳定且文件边界不重叠 | 改动、验证结果和未决事项 |

若两个子任务都会改同一个公共组件，先收敛接口或串行推进。把相互依赖的步骤硬拆并行，只会把等待变成 merge 冲突。

## 委派说明要能独立阅读

```text
请使用子 Agent，只读检查搜索功能的调用链和相关测试。
不要修改文件，不读取凭据。
请返回入口路径、关键状态变化、已有测试覆盖和可验证的风险。
主 Agent 负责确定修改方案并整合结果。
```

使用 Codex 的子 Agent 入口和配置时，以当前客户端实际能力为准。独立开发可使用不同 worktree；它隔离文件改动，却不会隔离同一数据库、同一外部账号或共享预览端口。

## 整合是一项单独的工作

主 Agent 要核对结论是否引用了实际文件、子任务是否跑过声称的检查、接口是否仍兼容。把各子任务的代码合在一起后，还要运行组合后的验证；分别通过构建不保证合在一起仍然通过。

出现冲突时先理解双方意图，再决定保留什么，不能机械地选择「全部接受当前版本」。是否值得多 Agent，最后看完成一个可审查结果的总耗时和总成本，而不是看同时开了几个会话。
