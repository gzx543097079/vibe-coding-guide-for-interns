title: 上下文管理
description: 给 Agent 恰好够用的信息：文件范围、会话切分与压缩。
---

上下文管理的目标是**让 Codex 拿到这次判断所需的信息，并能追溯信息来源**。窗口再大，重复日志、过时方案和不相关文件也会干扰工作；限制文件范围同样不能省掉必要的调用方和测试。

## 按问题提供材料

修复问题时，先给复现步骤、完整错误、项目实际版本和相关入口；实现功能时，给预期行为、可复用组件、接口契约和验收标准。路径比「看一下登录相关代码」更明确，但不必在不了解项目时编造路径，让 Codex 先定位也可以。

用本仓库举例：修改章节正文主要看对应 Markdown；调整导航还要看 `modules.ts`；修改折叠步骤则需要同时看组件和共享样式。只提供截图，无法说明组件的真实约束。

## 长会话在什么时候切开

同一任务中的定位、修改和验证可以保留在一个会话里。任务目标改变、历史已有多条互相冲突的路线，或者反复解释同一约束时，更适合整理结果再开新会话。切开之前先保存必要事实：

```md
目标：修复搜索请求的竞争条件。
当前结论：旧响应会覆盖新输入；接口本身无异常。
相关位置：页面、请求函数和回归测试的实际路径。
已验证：测试命令、结果，以及对应 commit。
未完成：移动端交互检查；不涉及接口改动。
下一步：先复现，再修改响应提交条件。
```

这是一份交接说明的结构示意，路径和结果必须填写实际证据，不能把「准备测试」写成「测试通过」。

## 压缩之后重新核对关键细节

历史摘要可能省略报错原文、数值和否决过的方案。涉及金额、权限、接口字段或失败原因时，重新读取原始来源；不能仅因为摘要中出现过某个说法，就当作已确认事实。长期约定放进 [AGENTS.md](./rules-files)，当前任务的临时状态放进交接记录，两者分开维护。
