复杂协作的难点通常是**状态、接口和责任没有同步**，而不是缺少一段更长的提示词。多仓库、多会话或多人同时工作时，先确定任务归属与交付边界，再让 Codex 执行。

## 明确谁负责什么

接口变更由谁确认、哪些仓库要同时发布、数据库迁移由谁执行、最终谁有合并权限，都需要写清。Agent 可以起草方案和代码，但不能代替业务负责人决定兼容策略。

| 需要同步的内容 | 可持久保存的位置 |
| --- | --- |
| 长期工程约定 | 项目规则和贡献说明 |
| 接口与事件契约 | 版本化的接口文档和契约测试 |
| 当前任务状态 | Issue、设计文档或交接记录 |
| 实际变更与验证 | commit、PR 和 CI 记录 |

## 以兼容窗口组织跨仓库改动

假设调用方要使用一个新字段。先让服务端兼容旧请求并返回新字段，再升级调用方，观察旧调用是否仍存在，最后按约定移除旧行为。这个例子说明发布顺序，不代表所有系统都必须采用同一种方案。

只在两个仓库各自「构建成功」还不够，要验证真实接口组合。工作流中的重试、错误格式、超时和权限同样属于契约，不能只同步字段名称。

## 交接时写事实和未完成项

```md
当前目标：为列表接口增加可选过滤条件。
范围：服务端解析与客户端调用；不修改已有字段含义。
依赖：先发布兼容旧请求的服务端版本。
证据：具体 commit、测试命令与结果。
未完成：部署顺序确认、目标环境联调。
下一步负责人：由任务记录明确指定。
```

会话中断后，接手者应先读当前代码和记录，再复现关键检查。文档里写「已完成」却没有对应提交或输出，要当作待核实。集成后由一个明确的负责人检查组合结果，避免每个参与者都以为最后一步属于别人。
