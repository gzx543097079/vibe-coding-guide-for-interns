前端架构要让**一次业务变化有清楚的修改位置和验证范围**。目录分层、设计系统和微前端只是手段；如果改一个按钮必须理解整套平台，抽象可能已经超过问题本身。

## 先稳定依赖方向

页面组织业务流程，业务模块处理该领域的状态与规则，公共层提供稳定的基础能力。公共组件不应反向依赖某个具体页面，也不要让所有业务都通过一个不断增长的全局对象互相访问。

```text
页面入口 → 业务模块 → 基础组件 / 请求适配
                  → 领域数据与规则
```

这是依赖方向的示意，不是必须照抄的目录模板。已有项目先沿用现有边界；需要调整时从高频变化、循环依赖或难以测试的部分入手。

## 组件库和设计系统不只提供样式

把颜色、排版、间距与交互约定沉淀为令牌和组件，同时提供状态示例、可访问性、兼容范围和升级说明。业务组件抽入公共库之前，确认它表达的是共同能力，而不是两个页面暂时长得像。

| 方案 | 采用前要能回答 |
| --- | --- |
| 单应用按业务分模块 | 谁拥有接口和公共状态 |
| monorepo 共享包 | 版本、构建、测试和变更传播如何处理 |
| 微前端 | 独立交付的组织收益是否覆盖运行时与治理成本 |

## 工程化围绕可重复交付

锁文件、构建配置、类型检查、测试和 CI 共同决定结果是否可重复。增量缓存要覆盖影响产物的输入；开发服务器成功不能替代正式构建。框架升级或状态迁移应分阶段进行，避免和业务需求一起大范围重写。

让 Codex 提出架构调整时，要求列出现有痛点、修改边界、可测量目标、迁移步骤和撤回条件。没有具体问题时，优先保持简单，而不是为了「最佳实践」增加更多层。
