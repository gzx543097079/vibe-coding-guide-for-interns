---
title: 渲染原理
description: 浏览器和原生平台的渲染流程，以及卡顿从哪里来。
---

界面卡顿要先找到**主线程在忙什么、哪一帧没及时完成**。理解渲染流程可以帮助选测量工具，但不能只凭「用了 transform」就宣称动画流畅。

## 浏览器的一次更新

浏览器解析内容，计算样式与布局，绘制需要的像素，再把图层合成到屏幕。实际过程有增量更新和优化，不是每次状态变化都从头重做全部步骤。

| 改动类型 | 可能影响的阶段 |
| --- | --- |
| 内容、尺寸和位置关系 | 样式、布局及后续绘制 |
| 颜色、边框、背景 | 绘制，具体依实现而定 |
| 部分 transform / opacity 更新 | 可能主要影响合成，但有条件 |
| JavaScript 长任务 | 阻塞事件与主线程相关工作 |

合成层也有内存和管理成本；大量图层、大图片、滤镜和复杂裁剪可能使情况更差。不要给所有元素长期加 `will-change`。

## 避免读写布局交错

先修改样式再立刻读取尺寸，可能迫使浏览器完成待处理布局。若在循环里反复读写，开销会放大。将需要的尺寸集中读取，再批量更新；是否真的产生瓶颈，用 Performance 录制验证。

## 框架更新与平台渲染不是一回事

组件重新执行不一定导致 DOM 改动，DOM 改动也不一定导致整页重绘。原生和跨端平台有自己的布局与绘制过程；不能把浏览器中的经验直接当作所有设备的结论。

## 用一段录制解释问题

固定页面、数据量、设备和操作，录制卡顿发生前后的过程。观察长任务、布局、绘制和图片解码，再修改一个主要因素，对比相同操作。记录工具版本和设备条件；开发环境或模拟器的结果不能直接代表用户设备。

给 Codex 的材料应包括性能录制结论、相关组件与具体操作，而不是只说「优化一下」。确认改善后再扩大改动，避免同时换列表、动画和请求层导致无法归因。
