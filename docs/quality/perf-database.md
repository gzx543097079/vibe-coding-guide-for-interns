数据库优化从真实查询、参数与数据分布开始。看到全表扫描就加索引，或让 AI 只凭表结构猜瓶颈，都可能增加写入成本而没有改善用户等待。

## 先读执行计划

以 PostgreSQL 为例，下面依赖已经存在的 `orders` 表，只展示检查语法；请替换成测试环境的真实表与参数：

```sql
EXPLAIN
SELECT id, created_at
FROM orders
WHERE customer_id = 42
ORDER BY created_at DESC
LIMIT 20;
```

普通 `EXPLAIN` 展示计划和估算。关注扫描方式、估算行数、过滤、排序、连接顺序与成本；成本单位不是毫秒。小表、低选择性条件或需要大量记录时，顺序扫描可能合理。

## 实测不能忽视副作用

`EXPLAIN (ANALYZE, BUFFERS)` 会实际执行语句并增加测量开销。对写语句尤其危险；事务回滚也不能保证撤销外部函数调用等所有副作用。先在隔离测试数据上使用，并遵循环境授权。不要为获取计划直接执行未知生产写入。

读实际计划时，把估算与实际行数、循环次数、缓存和磁盘读取放在一起看。嵌套节点的耗时不能简单相加，父节点可能已包含子节点。缓存状态与统计信息不同，计划和时间也可能变化。

## 索引设计跟查询走

复合索引要结合过滤条件、排序和选择性评估，不能机械地按字段在 SQL 中出现的顺序创建。给每个字段加单列索引会增加空间和写入维护，仍未必满足目标查询。分页、返回列数量和不必要关联也值得检查。

修改前后使用相同数据和参数，记录查询延迟、计划、读写资源与其他关键查询的影响。更新统计信息、索引创建和表结构变更也可能带来锁与资源压力，不能未经计划在线操作。

给 Codex 提供脱敏 SQL、表与索引定义、数据量级以及计划，要求它指出证据支持的瓶颈和验证步骤。没有可连接的测试数据库时，计划建议应标为待执行，不编造运行时间或「已命中索引」结果。
