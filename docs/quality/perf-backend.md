后端慢请求可能在计算，也可能在等待数据库、连接池、锁或下游。先拆分请求时间，再决定优化哪一段，避免把「CPU 不高」理解成服务没有瓶颈。

## 读一条请求的时间线

记录接收、排队、查询、外部调用和响应序列化的耗时，通过请求 ID 关联。列表接口如果对每条记录再查一次关联表，就可能出现 N+1；即使单条 SQL 很快，累计次数和连接占用也会放大延迟。

查询次数增加时先看能否批量读取或合理关联，并检查返回数据量。不要只把串行改并行：无限并发会挤满连接池，把问题传给数据库或第三方。

## 压测需要工作负载说明

| 必须记录 | 为什么 |
|---|---|
| 接口、参数、数据规模 | 空库结果无法代表真实查询 |
| 并发或到达速率 | 两者对应不同压力模型 |
| 成功、失败和超时数 | 快速报错会制造好看的延迟 |
| p50 / p95 / p99 | 平均数掩盖长尾 |
| 下游与资源指标 | 定位等待和容量上限 |

压测只在获准的环境中进行，事先定义停止条件和清理方式。客户端自身达到瓶颈时，服务端数据也会失真。缓存冷暖、数据分布和后台作业应随结果一起记录。

## 优化必须保持正确性

连接池不是越大越好，池太大会让数据库争抢资源。缓存要定义过期与失效策略，避免把已变更的权限或库存当旧值使用。重试需要截止时间、退避与幂等语义，不能在系统过载时制造额外风暴。

每次只验证一个主要假设。例如先消除 N+1，比较查询次数、接口长尾和错误率，再考虑缓存。增加实例前确认瓶颈是否位于共享数据库；扩应用未必增加整体容量。

让 Codex 根据 trace 和查询记录提出修改，要求说明适用负载、正确性风险与回退方式。没有真实压测时，只能报告已完成代码检查或局部实验，不把模拟结果写成生产容量承诺。
