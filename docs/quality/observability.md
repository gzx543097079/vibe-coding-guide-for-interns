可观测性帮助你从系统输出判断内部发生了什么。日志、指标和 trace 需要围绕同一个用户动作关联，堆满日志并不会自动让问题更好查。

## 三类信号各有用途

| 信号 | 适合回答 | 设计重点 |
|---|---|---|
| 日志 | 某个请求具体经历了什么 | 结构化事件、必要上下文 |
| 指标 | 问题多大、是否持续 | 稳定维度、成功与失败都记录 |
| Trace | 请求在哪个环节等待 | 跨服务上下文与 span 边界 |

例如订单提交失败，先从错误率指标判断影响，再用请求 ID 找日志，最后通过 trace 查看库存或支付调用。缺少其中一类也能开始排查，但不能用单条日志推断全部用户都受影响。

## 设计关联字段

下面是脱敏事件结构示意，不是实际采集记录：

```json
{
  "event": "order.submit.failed",
  "request_id": "demo-request",
  "trace_id": "demo-trace",
  "service": "checkout",
  "duration_ms": 120,
  "error_code": "INVENTORY_TIMEOUT"
}
```

关联 ID 帮助定位，不代表身份授权；外部传入的字段也需要格式与长度限制。不要把 token、完整地址或请求体全集记录进去。指标标签避免用户 ID、订单号等高基数字段，否则存储与查询成本可能失控。

## 告警从用户影响出发

错误率、延迟和关键任务成功率通常比「出现一条 error 日志」更能反映服务问题。阈值、窗口与响应方式需要结合基线和业务约定；告警要写清负责人、排查入口与运行手册。没有行动路径的重复噪声会降低响应能力。

采样与保留策略也要记录：没找到 trace 可能是未采样，而不是请求没发生。观测链路故障不能拖垮业务；增加采集前测开销、脱敏与访问控制。

让 Codex 接入观测时先选一条关键链路，核对上下文能否跨服务传递、失败是否完整记录，再扩展。不要为了验证采集把生产隐私复制到测试平台，也不要在没有数据时编造告警恢复或服务可用率。
