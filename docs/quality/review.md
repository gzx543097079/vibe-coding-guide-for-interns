title: 验证与代码审查
description: 不盲信 AI 输出，逐行审 diff，识别不存在的 API。
---

审查要判断这次改动是否正确、能否维护和能否安全交付。先理解需求和 diff 的范围，再读关键调用链；格式建议不应淹没会丢数据或越权的问题。

## 从需求走到行为

先读 PR 的问题描述、复现方式和验收结果。新增了空状态，就检查无数据时实际走哪条分支；修改权限，就追到服务端校验；新增配置，就确认缺省值和已有用户如何迁移。只有改后的文件，通常看不出它破坏了哪个旧约定。

本地可先用 `git diff --stat` 判断规模，再用 `git diff` 看未暂存改动，`git diff --cached` 看准备提交的内容。审 PR 时比较的是目标分支与功能分支，别误把本地工作区差异当完整 PR。

## 按影响排序

| 检查方向 | 具体关注 |
|---|---|
| 正确性 | 空值、并发、失败分支、重复操作 |
| 安全 | 服务端授权、参数化查询、凭据与日志 |
| 兼容 | 公共 API、数据库迁移、旧客户端 |
| 验证 | 测试是否针对问题、是否实际执行 |
| 可维护 | 命名、职责、与现有实现的一致性 |

AI 可能凭记忆提到不存在的 API。遇到这类建议，要核对项目依赖版本、类型定义和官方资料。也要查看生成文件与锁文件是否出现无关修改，而不是只看主要业务文件。

## 有效反馈带条件和后果

「这里不好」没有行动信息。更有用的是：「当第一次请求晚于第二次返回时，此处会覆盖最新列表；请用请求编号限制提交，并增加乱序返回用例。」反馈定位到文件与行，解释触发条件、用户影响和验证方法；不确定的推断明确标注。

让 Codex 审查时提供需求、相关 diff 和约束，要求先报告可复现的缺陷及理由。它的建议需要人工判断，不能用「AI 说通过」代替测试和负责人审核。

提交前自己再走一遍关键流程，检查 PR 描述有没有夸大验证。审查中发现范围过大，可以拆成能独立验证的 PR；不要为了让 diff 好看而把必要迁移藏到另一个未说明的提交。
