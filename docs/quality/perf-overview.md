title: 性能优化总览
description: 先测量再优化，指标与工具的思路。
---

性能优化先定义用户遇到的等待，再测量它发生在哪里。没有基线，代码变短或换了框架都不能证明更快。

## 指标对应具体旅程

「打开商品页」可能包含首屏加载、接口等待和图片解码；「点击保存」要看到成功结果，也要确保数据正确持久化。先选定设备、网络、数据规模和操作，再确定目标指标及不能牺牲的错误率、准确性与资源限制。

| 指标 | 告诉你什么 | 容易忽略什么 |
|---|---|---|
| 延迟 p50 / p95 / p99 | 中位与长尾等待 | 失败请求可能没被计入 |
| 吞吐量 | 单位时间完成的工作 | 工作量与成功率是否相同 |
| CPU / 内存 | 资源压力 | 等锁或下游等待可能 CPU 很低 |
| 帧耗时 | 交互是否及时绘制 | 平均帧率会掩盖局部卡顿 |

分位数来自一组样本，不是把各机器的 p95 简单平均。样本太少、混合不同接口或只测成功请求，都可能得出误导结论。

## 建立可比较的基线

记录 commit、构建方式、硬件、输入、并发、缓存状态和测量工具。区分冷启动与预热状态，重复采样并保留原始记录。修改前后使用同一方案；设备发热、后台进程和测试环境共用资源都应记录。

先通过调用栈、时间线或 trace 找最贵路径，再只改变一个主要因素。比如列表慢，先确认是请求、数据转换还是绘制；直接加缓存可能掩盖旧数据问题，也可能没有减少真正耗时。

## 用结果决定下一步

优化报告写清瓶颈证据、改动、同条件前后结果和副作用。若差异落在测量波动内，就不能宣称提升。吞吐变高而错误率上涨，也不算达成原目标。

向 Codex 提供脱敏的测量记录和相关代码，让它提出可证伪的解释、最小实验与回退方法。原始数据还没有时，先让它帮助设计测量，不让它根据函数名编造百分比。达到目标就停止继续堆叠复杂度，把成本留给更重要的用户问题。
