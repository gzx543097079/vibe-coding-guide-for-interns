前端性能需要同时看加载与交互。先确认用户等待的是资源下载、脚本执行、布局绘制还是接口，再针对那一段改动。

## 分开测首屏和操作

用发布构建记录一次冷加载和一次常用交互，例如打开弹层、输入筛选、滚动长列表。开发模式的调试逻辑和源码转换会干扰比较。记录浏览器版本、视口、设备和网络条件；DevTools 的限速有助复现，但不能替代目标设备。

Network 面板适合查看请求数量、资源大小、缓存命中与瀑布图。Performance 时间线帮助找主线程任务、脚本、布局和绘制。看到大文件不代表它阻塞了当前交互，必须对齐时间线和用户动作。

## 从证据选改动

| 观察 | 下一步检查 | 可能的处理 |
|---|---|---|
| 首屏图片很晚出现 | 尺寸、下载与解码 | 合理图片规格、预留空间 |
| 输入后长时间无响应 | 主线程堆栈 | 拆分任务、减少同步计算 |
| 列表滚动卡顿 | DOM 数量、布局频率 | 分页或虚拟化，检查动态高度 |
| 页面反复跳动 | 图片与异步内容占位 | 稳定尺寸和布局 |

延迟加载也有取舍：非首屏资源可以推迟，首屏关键内容被推迟反而会更慢。虚拟列表减少 DOM，但需要额外处理焦点、读屏和滚动位置，不能只比较节点数量。

## 避免无效优化

不要对每个函数都缓存，也不要给所有 CSS 属性加过渡。频繁交错读取布局与写样式可能引发反复计算；先在时间线确认，再合并更新。大面积模糊、阴影和动画也应在目标设备检查，动效同时尊重减少动态效果偏好。

优化后用同一输入重测，并检查键盘操作、加载失败、空数据和慢网络。报告保留时间线与构建版本，不只贴一个 Lighthouse 分数；单次实验室评分不等于所有真实用户体验。让 Codex 根据采样记录解释最贵路径，并为每个建议列出预期收益与验证方法。
