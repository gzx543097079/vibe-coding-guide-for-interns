好的提示词让任务可以开始，也让结果可以检查。先写预期行为、相关上下文和验收方式，再补确实必要的约束；不需要把每个小改动写成长篇角色设定。

## 从模糊要求变成可执行任务

「做个更好的搜索」没有边界。可以改成下面这段，路径需要替换成实际文件：

```text
目标：搜索框连续输入时，只展示最后一个关键词的结果。
现状：较早发出的请求晚返回，会覆盖新结果。
范围：先阅读【搜索组件】及其调用的【请求函数】。
约束：沿用现有依赖，不修改 API 协议和其他页面。
验收：用两次乱序返回证明旧成功或旧失败均不覆盖最新结果；
保留加载、空数据和失败提示。
输出：完成必要改动，报告原因、diff 和实际执行的检查。
```

这里有目标、上下文、约束、验收和输出格式。五项是帮助补齐信息的工具，不是必须逐字照抄的模板。若项目已经提供测试命令，引用维护文档即可；不要复制一份容易过期的规则。

## 验收标准写观察结果

「代码优雅」「体验顺滑」不易判断。改成「按 Escape 关闭弹层并回到触发按钮」「空数组返回零」「跨租户请求被拒绝」就能检查。也要说明不属于本次范围的行为，避免 AI 顺手扩展功能。

提供一个正常例子和一个关键反例往往足够起步。对于金额、时区和权限，规则本身不能让 AI 猜；信息缺失就说明尚待决定，而不是让它自行编一个业务约定。

## 按任务选择协作节奏

边界明确、可回退的改动可以直接实施并检查。跨模块方案或需求有歧义时，先比较方案再决定。不要把「每一步都等确认」写成所有任务的默认流程，也不要把「不用问」理解成可以执行任何外部操作。

结果回来后对照验收，检查改动范围和验证证据。提示词可以减少误解，但不能保证 API 正确、逻辑无误或测试真的运行。把有效的项目规则沉淀到维护文档，把本次输入留在任务里。
