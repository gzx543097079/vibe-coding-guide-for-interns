这页用于任务前后快速核对。命令应在确认过的仓库与环境中运行；团队流程优先于速查，未理解作用的命令不要直接复制。

## Git 的日常只读检查

| 目的 | 命令 | 注意 |
|---|---|---|
| 看工作区与分支 | `git status --short --branch` | 未跟踪文件也需判断归属 |
| 看改动规模 | `git diff --stat` | 不能替代读实际内容 |
| 看未暂存内容 | `git diff` | 不含已暂存和未跟踪内容 |
| 看待提交内容 | `git diff --cached` | commit 前检查 |
| 看提交摘要 | `git log --oneline -5` | 先确认所在分支 |
| 检查空白错误 | `git diff --check` | 不检查业务正确性 |

添加文件时明确列出路径，避免把凭据、生成产物和用户文件带入提交。提交、推送和 PR 创建会写入本地或远端；按照项目约定在功能分支进行，不在主分支直接提交，也不为省事改写共享历史。

## 本仓库的开发入口

```bash
npm run dev
npm run build
npm run preview -- --port 4189
```

开发、构建与预览是不同阶段。预览读取上一次构建产物，检查修改前先构建，再启动自己的预览端口；不要停止他人的进程。依赖首次安装可在干净检出目录运行 `npm ci`，它会重新准备依赖目录。

## 任务的最小证据

开始时写清预期行为、相关文件、约束与验收；结束时检查实际 diff、适用测试、构建和未验证项。修 bug 附复现与回归，性能优化附同条件测量，UI 附关键状态、键盘与窄屏检查，发布附环境与恢复路径。

遇到环境缺失，应报告「没有运行」及原因，不把静态阅读写成通过。示例能运行也不代表满足生产的鉴权、数据和容量要求。

## 容易让任务失控的做法

「先全局替换再说」会误伤无关语境；「测试绿了就行」可能忽略无效断言；「AI 推荐就引入」会增加维护与许可负担。把检查放到对应风险旁，先做最小可验证改动，再决定是否扩展。

不把一套清单变成每个任务都要执行的固定仪式。文案修正、状态逻辑和数据迁移的验证成本不同，选择能证明当前结果的检查即可。
