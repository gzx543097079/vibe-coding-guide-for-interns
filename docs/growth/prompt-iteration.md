迭代应补充证据、缩小差异和验证假设。第一次结果偏了，先指出哪里不符合预期；只说「再优化一下」通常会让改动继续扩大。

## 纠偏给具体对照

例如要求弹层关闭后恢复焦点，结果只实现鼠标点击。追问可以写：「当前按 Escape 已关闭，但焦点落在页面根节点；请沿触发按钮引用恢复焦点，并验证键盘往返。只改弹层组件。」这比要求「更专业」更容易执行和验收。

保留有效部分，撤回不相关部分。新需求应单独说明，避免让 AI 误以为之前的所有约束都失效。任务进行中补充限制时，也应指出是否影响已完成步骤。

## 复杂任务先找决策点

跨模块修改可以先列输入输出、数据流、兼容风险和拆分步骤，只有真实存在选择或影响时再确认。对已经明确的小步骤，直接实施并检查更合适。计划不是成果，生成计划后还需要把已授权工作做完。

每步都应留下可检查的结果：一个函数、一条能运行的链路、一份测量记录。若一步只能交付大量未连接的文件，就继续拆分。

## 重复失败时换方法

| 现象 | 应补充的动作 |
|---|---|
| 反复改同一行但报错不变 | 核对构建入口和完整错误栈 |
| 修 A 又破坏 B | 找共享状态与补回归用例 |
| AI 坚称 API 存在 | 查安装版本、类型与官方文档 |
| 输出越来越偏离目标 | 重述目标与已确认事实，缩小范围 |

不要用一串失败命令堆成「努力过」的证明。连续尝试没有带来新证据时，停下修改，重新做最小复现或请熟悉模块的人检查关键假设。

## 收尾保留当前状态

让 Codex 报告已改什么、实际执行什么、还有哪些失败或限制。未通过的检查应给出原始错误要点和下一步，不应删掉测试掩盖它。长任务可以把已确认决策、工作分支和未完成项写进交接文档，继续时先读当前代码，避免依赖旧对话记忆。
