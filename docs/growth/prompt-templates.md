模板适合提醒自己补齐信息，复制后要删掉不适用的部分。把真实路径、输入和验收填进去，才能成为任务；带着【占位符】直接发送，仍然会让 AI 猜。

## 选和当前问题匹配的模板

| 任务 | 本页模板 | 应补的关键证据 |
|---|---|---|
| 新增功能 | 写新功能 | 使用场景、参考实现、验收行为 |
| 修复错误 | 修 bug | 复现步骤、实际与预期、错误原文 |
| 改善结构 | 重构 | 行为边界、现有测试、允许范围 |
| 补测试 | 写测试 | 输入规则、边界和异常预期 |
| 审查 PR | 代码审查 | 改动目的、diff、相关调用方 |
| 性能优化 | 性能分析 | 同条件基线、时间线与目标 |

本页还保留读代码库、Git / PR、文档、前端 UI 和后端 API 模板。它们提供不同任务的检查线索，不代表必须同时启用。

## 发送前做一次替换

例如用修 bug 模板时，把「相关代码」换成真实文件与函数，把「复现步骤」写到其他人能重复操作的程度。报错尽量保留关键栈，但先脱敏。若不知道根因，就明确要求定位证据，不要提前把自己的猜测写成事实。

验收不要停在「正常运行」。前端 UI 要描述键盘、空数据和失败状态；API 要描述状态码、授权边界和重复请求。测试命令优先沿用项目现有入口，缺少环境时要求说明未验证项。

## 调整确认方式与改动权限

部分通用模板采用「先给方案、等确认」的教学节奏。需要协商方案时可以保留；对于已经授权、范围明确的日常修改，可以改成「按项目约定直接实施，完成后报告检查」。确认方式应由任务决定，不能让模板覆盖用户已给出的授权。

外部发布、凭据访问和数据删除也不能靠一段提示词扩大权限。读仓库与改代码、部署到生产、向别人发送内容是不同动作，分别按任务范围和团队流程处理。

## 保存有效版本

模板改好后，记录它解决了什么问题和仍会失败的场景。把可复用规则放进项目约定；不要把业务隐私、临时日志和过期路径永久塞进共享模板。模板是否有效，最终看结果和验证，不看措辞是否像专家。
