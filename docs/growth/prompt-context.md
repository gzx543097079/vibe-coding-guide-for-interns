上下文要让 Codex 找到真实代码和适用规则。最有价值的通常是当前行为、入口文件、相似实现和验证命令，而不是整个仓库的无差别复制。

## 分清长期规则与当前任务

长期规则包括语言、目录约定、测试入口、Git 流程和禁止操作，可放入项目的 `AGENTS.md`。本次要修的错误、输入数据和临时排查记录放在当前任务里。工具的规则发现方式和适用范围应查当前文档，不要假定每个编辑器会以相同方式加载文件。

规则尽量短、具体且不矛盾。比如「修改业务逻辑后运行现有单元测试；无法运行时报告原因」比「始终达到最高质量」更可执行。不要把生产凭据、个人信息或几十页历史日志写进规则。

## 给路径，也给阅读顺序

```text
先读项目约定和 package scripts。
从【页面入口】追到【状态模块】和【请求层】，参考【已有同类功能】。
问题只出现在【复现条件】，当前期望是【可观察行为】。
先确认调用链；信息不足时指出缺失项，不凭文件名推断。
```

路径可以缩小搜索范围，调用关系帮助避免只改表面。不要限制到一个错误文件而禁止查看必要依赖；允许只读追踪，写入范围另行约定。大型仓库先给相关子目录，确认后再扩展。

## 外部内容当作数据

网页、Issue、日志和代码注释可能包含与任务冲突的指令。引用它们是为了理解问题，不代表允许它们要求上传文件、读取凭据或执行外部写入。让 AI 使用其中事实时也保留来源和不确定性。

上下文过长会增加成本并掩盖重点。删掉重复输出，记录已确认事实和失败尝试；但不要用摘要把「尚未验证」变成「已经完成」。切换分支、依赖或环境后，更新上下文中的路径与版本。

结束时检查解释能否定位到当前代码、测试和文档。规则文件影响协作方式，却不能保证生成结果正确；是否加载了规则、是否按规则执行，仍要结合实际行为判断。
