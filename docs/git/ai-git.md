让 Codex 使用 Git 的目标是**保留清楚的改动边界和可靠的恢复位置**。生成得快不是跳过 diff 的理由；反而因为一次可以修改更多文件，更需要及时检查范围。

## 开始前先看现场

```sh
git status --short --branch
git diff --stat
git log -5 --oneline
```

分清当前分支、已有未提交改动和任务起点。如果有别人留下的文件，不要为了得到「干净状态」把它们清掉；记录并绕开无关内容，必要时使用独立 worktree。

## 给 Codex 的任务边界

```text
在功能分支修复搜索失败后按钮无法恢复的问题。
开始前检查现有改动，只修改页面和相关测试。
不升级依赖，不改公共接口，不清理无关文件。
完成后列出实际改动和验证结果；提交前先审 diff。
不要合并或推送到 main。
```

提交前看 `git diff` 和暂存区差异，确认没有把格式化、锁文件和生成产物混入。一个 commit 对应一个可以说明的意图，不必为了「小步」把紧密依赖的实现拆成不可运行的片段。

## 让验证跟上真正的改动

代码修复应覆盖原失败场景；移动文件还要检查导入；修改配置要验证实际构建。Codex 的总结不是命令输出，声称通过的检查应能找到对应执行记录。

当任务中途改变方向，先保留已经有价值的工作，再决定后续提交。需要撤销已共享的错误改动时，通常通过新的反向提交表达；改写历史和清理工作区具有不同风险，应由维护者根据现场决定。

PR 中把限制写清，例如只检查了浏览器模拟视口、没有跑真机。不能把「代码已生成」记成「功能已验证」。
