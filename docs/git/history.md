title: 改写历史
description: rebase -i、cherry-pick、reflog：整理提交、找回丢失的改动。
---

整理历史之前先分清：**提交是否已经共享，工作区是否有未保存的内容，能否用新增提交解决问题**。改写会产生新的提交身份，不能用来掩盖错误或替代团队的审查记录。

## 三种工具解决不同问题

| 工具 | 作用 | 常见边界 |
| --- | --- | --- |
| rebase -i | 调整一组本地提交的排列与内容 | 仅在允许改写的个人功能分支使用 |
| cherry-pick | 把指定提交的改动应用到当前分支 | 新提交可能与原上下文不兼容 |
| reflog | 查看本地引用移动的记录 | 不是远端备份，也不永久保留 |

在新建的练习仓库或未发布的个人分支中，`git rebase -i HEAD~2` 可以打开最近两个提交的编辑清单。执行前要确认确实存在两个可整理的提交，并理解编辑器中的动作；不要在本仓库的 `main` 或共享历史上练习。

## 需要一个特定修复时

先用 `git show <commit>` 阅读内容和依赖，再在目标功能分支执行 `git cherry-pick <commit>`。尖括号部分要替换为实际提交标识。处理冲突后重新运行目标分支的检查，原分支上的通过记录不能直接沿用。

## 找回引用时先建恢复分支

```sh
git reflog --date=iso -10
```

从输出中定位丢失改动所在的提交，先用 `git show` 核对；确认后用 `git branch recovery/checked <commit>` 创建引用，避免立即移动当前分支。reflog 只能帮助找回仍保存在本地对象库中的提交，不会自动恢复从未提交的文件内容。

## 已经共享的错误用新的记录纠正

通常先考虑 `git revert <commit>`，它创建一个反向改动的新提交。合并提交、后续依赖和数据库迁移需要额外判断，不能机械照抄撤销命令。遇到不明确的现场，先保留状态并请维护者确认，不进行强制推送。

继续查阅：[交互式 rebase](https://git-scm.com/docs/git-rebase)、[reflog](https://git-scm.com/docs/git-reflog)、[revert](https://git-scm.com/docs/git-revert)。
