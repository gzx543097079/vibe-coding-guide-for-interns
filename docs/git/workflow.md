分支模型服务于**发布频率、版本支持和团队协作**。选择名字熟悉的模型，不能代替回答「变更怎样进入生产」「紧急修复怎样回流」这些问题。

## 短分支与发布分支

| 方式 | 适合的组织方式 | 需要承担的成本 |
| --- | --- | --- |
| 短期功能分支、频繁集成 | 自动检查完善，持续发布 | 小步交付、功能开关和稳定主线 |
| 长期发布分支 | 同时支持多条产品版本 | 修复回流、重复验证和分支差异 |
| GitFlow 类流程 | 有明确阶段和多个长期分支 | 更多 merge、环境和发布协调 |

长期分支不天然更安全，短分支也不天然更高效。分支活得越久，越容易积累与主线的差异；减少冲突依赖稳定接口和及时集成。

## 把 tag、产物和环境关联起来

tag 标记一个提交位置，不等于构建产物本身。发布记录应说明提交标识、产物摘要、配置、迁移和目标环境。测试环境通过的产物应按既定流程晋升，避免在每个环境重新构建出不同结果。

```text
发布记录示意
版本：按团队版本规则填写
源码：完整 commit 标识
产物：构建标识与摘要
依赖：数据库迁移或配置变化
恢复：上一个可用产物与兼容条件
```

## 版本号表达兼容性

语义化版本的主版本、次版本和修订号分别表达不兼容变更、向后兼容的功能和修复，前提是项目已经定义公共接口。内部应用也要说明版本规则，不能只看数字大小猜测是否可以直接升级。

紧急修复如果从旧发布分支产生，要明确哪些后续分支还需要这个修复，并重新验证。只把生产环境临时改好，却没有把改动回到源码与后续版本，会让问题在下次发布重新出现。
